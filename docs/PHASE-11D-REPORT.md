## 2. 足したテスト（28件）

### いちばん大事なもの — 門で止まっているか

| 確かめたこと |
|---|
| `Authorization` が無ければ 401 |
| `Bearer ` が付いていなければ 401 |
| 中身を書き換えたトークンは 401 |
| 期限切れのトークンは 401 |
| 別のプロジェクト宛のトークンは 401 |
| **通らなかった依頼は、Gemini まで1回も届かない** |

最後の1行が要点です。401を返していても、**その前に上流を叩いていたら意味がありません。**
呼び出しの記録を取って、0回であることを直接確かめています。

### APIキーが外に出ないこと

| 確かめたこと |
|---|
| 鍵はURLに付き、返事の本文には出てこない |
| **Gemini が失敗しても、鍵は返事に混ざらない** |
| **Cloudflare のログにも、鍵は残らない** ← ここで問題が見つかりました（第4章） |
| 鍵が長くても、切り詰めのすき間から漏れない |
| 動作確認の画面にも、鍵は出てこない |

Gemini はキーが不正なとき `"API key not valid: AIza..."` のように**エラー文にキーを含めて返します**。
上流の本文をそのまま扱う作りだと、そこから漏れます。

**返事のほうは、もともと本文を捨てていたので漏れていませんでした。**
漏れていたのはログのほうです。第4章に書きます。

### 上流の失敗の伝え方

429 は「混み合い」、500番台は「つながらない」、400番台は「断られた」。
どのモデルで失敗したかも返します（設定間違いの切り分けのため）。

### 記録に何を残すか

Cloudflare のログには **誰が使ったか（uid）と本文の大きさだけ**を残し、
**食事の中身は残しません。** 「AIには最小限だけ渡す」と決めた意味が、
ログで台無しにならないよう固定しました。

### 入口の作法

CORS、405、413（大きすぎる本文）、鍵が未設定のときの 500、動作確認の画面。
**断るときにもCORSの印を付ける**ことも確かめています。これが無いと、
ブラウザは応答そのものを読めず、画面には原因の分からない失敗しか出ません。

## 4. ⚠ 直した問題 — APIキーがログに残っていました

### 何が起きていたか

テストを書いている最中に、出力を見て気づきました。

```
{"uid":"user-123","result":"error","status":400,
 "detail":"{\"error\":{\"message\":\"API key not valid: AIza...\"}}"}
```

失敗の理由を Cloudflare のログに残す処理で、**上流の応答本文をそのまま書いていました。**

コードにはこう書いてありました。

> APIキーは URL のクエリにあり、応答本文には含まれません。

**この思い込みが間違いでした。** Gemini は、キーが不正なときに
`{"error":{"message":"API key not valid: AIza..."}}` のように
**エラー文にキーを入れて返します。**

利用者への返事は本文を捨てているので漏れません。**漏れていたのはログのほうです。**

### なぜ重いか

外部に公開されているわけではありません。Cloudflare の管理画面を見られる人だけです。

ただ、**これが起きるのは「キーがおかしいとき」**です。
つまり、**ログを見て、誰かに相談しようとする場面**そのものです。
画面を撮って送った先に、キーごと渡ります。

「APIキーをGitHubへコミットしない」と決めたのと同じ理由で、ここも塞ぐべきでした。

### 直したこと

ログに書く前に、キーを伏せ字にします。

```
detail: redact(text, env.GEMINI_API_KEY).slice(0, 500)
```

**伏せてから切ります。** 先に500文字で切ると、切れ目でキーが半分になり、
前半だけがログに残ります。テストでその順序も固定しました。

原因を追える情報（状態コード・利用者ID・エラーの文面）は、そのまま残ります。

### ★ Cloudflare への貼り直しが要ります

`worker.js` を変更しました。**Cloudflare の管理画面に貼り直してください。**
貼らないかぎり、いまのWorkerはキーをログに書き続けます。

## 5. ⚠ 未対応の問題 — レート制限が実装されていません

### 事実

設計書は3か所で、こう書いています。

> §7.6 濫用 … Workers KV に uid ごとの日次カウンタ。**既定 1日50回まで**
> §9.2 Worker が担うこと #2 … レート制限
> §13 Phase 8 … Cloudflare Worker（IDトークン検証・**レート制限**・Gemini実装）✅

**`worker.js` に、回数を数える処理はどこにもありません。**
`rate_limited` という文字列はありますが、それは
**Gemini 側が 429 を返したときに、それをそのまま伝えているだけ**です。
こちらでは1回も数えていません。

Phase 8 に ✅ が付いているので、**できているものと思われていたはずです。**
設計書の該当箇所は、実態に合わせて「未実装」と書き直しました。

### どれくらい危ないか（正直に）

**すぐに何かが起きる状態ではありません。**

- この入口は**ログイン証明が必須**です。誰でも叩けるわけではありません
- 通せるのは、あなたが `users` に登録した、有効なアカウントだけです
- トークンの寿命は1時間です

現実的に起こりうるのは、次の3つです。

| 起きること | 結果 |
|---|---|
| アプリの不具合でAIを呼ぶ処理が繰り返される | 無料枠が尽きる |
| 契約者が面白がって連打する | 同上 |
| 端末を盗られてトークンが漏れる（1時間以内） | 同上 |

**結果はどれも「Gemini の無料枠が尽きて、翌日まで全員のAIが止まる」です。**
データが漏れるわけでも、お金がかかるわけでもありません（カードを登録していないため）。

**直すべきですが、緊急ではありません。**

### 直すには

Cloudflare KV（無料枠内）に uid ごとの日次カウンタを持たせます。
コードは20行ほどですが、**あなたの手作業が1つ増えます。**

1. Cloudflare の管理画面で KV 名前空間を1つ作る
2. Worker に結び付ける（バインド名を決める）
3. 新しい `worker.js` を貼り直す

### もうひとつ、細かい話

本文の大きさの判定が `body.length` になっています。これは**文字の数**で、バイト数ではありません。
日本語は1文字3バイトなので、上限2,000,000は**実際には約6MBまで通ります。**

写真は base64（半角）なので、写真の経路では意図どおりに効いています。
文章だけで6MBを送るのは現実的でないため、**害はほぼありません。**
直すなら `new TextEncoder().encode(body).length` です。
