# Phase 10 報告 — トレーナーのコメントと AI評価

設計書 §13 の Phase 10（AI評価）です。あわせて §11.3 A-8 のトレーナーのコメント欄を入れました。

---

## 1. 何を作ったのか

日別画面の下に、**言葉が並ぶ場所**を2つ作りました。

```
日別画面
 ├ 食事 / 運動 / 体重 / 合計      … 数字
 ├ トレーナーのコメント            ← 人が書く
 └ AIの評価                        ← AIが書く
```

**順番に意味があります。** 人が書いた言葉が先に目に入るようにしてあります。
AIの文章は、そのあとの参考です。逆にすると、AIの講評が主役に見えます。

そして、**2つを混ぜていません。** 別のコレクションに保存しています。
同じ欄に並べると、契約者は「これはトレーナーが言ったのか、機械が言ったのか」が
分からなくなります。指導の記録として、そこは曖昧にできません。

---

## 2. トレーナーのコメント

| | |
|---|---|
| 場所 | `clients/{cid}/days/{date}/notes/{noteId}` |
| 書ける人 | **管理者のみ** |
| 契約者 | 読むだけ |
| 1件の上限 | 2000文字 |
| 編集・削除 | 管理者ができる |

### 契約者が書けないのは、UIを隠しているからではありません

Rules 側で塞いでいます。

```
match /notes/{noteId} {
  allow read: if canRead(cid);
  allow write: if isAdmin();
}
```

**ここは実装中に直した本当の穴です。**
最初は `mayEdit`（過去編集ウィンドウの判定）を使って書いていました。
つまり、**契約者が自分でトレーナーのコメントを書き換えられる状態**でした。
指導の記録が本人の手で変えられるなら、記録として成り立ちません。

### 確定済みの日にも書けます

1日の確定は「今日はもう食べません」という契約者の意思表示です。
トレーナーが黙る合図ではありません。むしろ確定したあとに書くほうが自然です。

## 3. AI評価

### 押したときだけ作ります

1日確定のたびに自動生成する形も考えましたが、やめました。
確定は解除して付け直せるので（Q14の決定）、そのたびにAPIを叩くことになります。
無料枠は有限なので、**回数は人が握れる形**にしています。

ボタンは契約者・管理者の両方が押せます。書けたその場で両方に見えます。

### 1日につき1件だけ持ちます

| | |
|---|---|
| 場所 | `clients/{cid}/days/{date}/review/latest` |
| 履歴 | **残さない** |

何度でも書き直せますが、古い評価は消えます。
評価は「いまの記録に対する言葉」です。記録を直したあとの古い評価に意味はありませんし、
溜めると無料枠を食います。

### AIに渡しているもの

```
合計（kcal / P / F / C）
目標（kcal / P / F / C）
運動の分数
食事の記録件数
登録待ちの件数
評価モード
```

**これだけです。** 契約者ID・名前・生年月日・体重は送っていません。

> 「AIには必要最小限の情報のみ渡す。契約者ID等をAIに送る必要がない場合は送らない。」

数字と差分だけで講評は書けます。誰の数字かをAIが知る必要はありません。

## 4. 安全の作り方 — 2層にしています

### 第1層: 指示文

システムプロンプトで、診断・病名・極端な方法を禁じています。

**ですがこれは「守られることを期待している」だけです。** 確かめてはいません。
モデルが変われば挙動も変わりますし、言い回し次第ですり抜けます。

### 第2層: 決定論的な検査（`@pt/core` の `checkReviewText`）

出てきた文章を、**表示する前に機械的に検査**します。25件のテストで固定しています。

| 検査 | 例 | 引っかかったら |
|---|---|---|
| 体に負担のかかるやり方 | 断食 / 絶食 / 食べるな / 水だけ / 下剤 | 表示しない |
| 病名・診断・治療 | 糖尿病 / 高血圧 / 診断 / 受診 / 処方 / 血糖値 | 表示しない |
| 長さ | 10文字未満・1200文字超 | 表示しない |

**「体に負担のかかるやり方」を先に判定します。** どちらにも当たる文章のとき、
利用者に伝わる理由がより重いほうになるためです。

#### わざと止めていないもの

疲れ・むくみ・だるさ、といった一般的な体調の話は通します。
そこまで止めると、**食事指導として当たり前の会話までできなくなります**。
止めたいのは「診断」と「治療」に踏み込む文章です。

#### 迷ったら出さない

AI評価は無くても記録は成り立ちます。
一方、まずい文章が1回届くほうの害はずっと大きい。釣り合っていないので、疑わしいものは止めます。

### 免責は必ず出します

評価があってもなくても、欄の下に固定で出します（設計書 §13 リスク12）。

> 食事と運動の記録にもとづく参考意見です。**医療的な判断ではありません。**
> 体調に不安があるときは、専門の方にご相談ください。

## 5. 実際に動かして直したこと

ここは実機の出力を見てから3回直しています。**指示文は机の上では完成しません。**

### ① 書かれていないことを足していた

最初の実物にこう出ました。

> 「忙しいスケジュールのなかでも」
> 「習慣化しようとする意識が伝わってきます」

**どちらも記録に書いてありません。** AIが想像で足した文章です。
設計書 §12 に「書かれていないことを足さない」と決めてあったのに、
**その原則を評価の指示文に入れ忘れていました。**

指示文に「■ 相手のことを想像しないでください」を追加し、×／○ の実例を添えました。

### ② 同じことを2回書いていた

「運動25分」が1つの講評の中に2度出ました。
「同じことを2回書かないでください」を追加。

### ③ 定型の前置きが付いていた

「できている点としては」で始まる、テンプレートのような文章になっていました。
「前置きを付けないでください」を追加。

### ④ 指示文の言葉がそのまま出ていた

こちらが書いた「数字として残る」という表現が、そのまま講評に混ざっていました。
「この指示文の言葉を、そのまま文章に使わないでください」を追加。

### ⑤ 食事0件の日にPFC不足を並べていた

何も食べていない日に「タンパク質が◯g不足しています」と出ます。当たり前で、意味がありません。
「食事の記録が0件の日は、最初にそれを伝えてください」を追加し、
その日は不足の羅列をしないようにしました。

**①〜⑤はすべて、実際の出力を見て確認済みです。**

## 6. Rules

```
match /clients/{cid}/days/{date}/notes/{noteId} {
  allow read:  if canRead(cid);
  allow write: if isAdmin();          // ← 契約者は書けない
}

match /clients/{cid}/days/{date}/review/{docId} {
  allow read:   if canRead(cid);
  allow create, update:
    if canRead(cid)
    && docId == 'latest'              // ← 1日1件に固定
    && request.resource.data.text is string
    && request.resource.data.text.size() >= 1
    && request.resource.data.text.size() <= 1200;
  allow delete: if canRead(cid);
}
```

`docId == 'latest'` を Rules 側で縛っています。
アプリが正しく書いているから大丈夫、では守りになりません。

## 8. お願い（毎回同じですが、大事なので）

`firebase/firestore.rules` の**判定を**変更した回は、
**Firebase コンソールに手で貼り直す必要があります。**

CIはルールを**テストするだけで、反映はしません**。
貼り忘れると、画面は動いているのに書き込みだけが静かに拒否されます。
Phase 9 の「登録依頼が積まれない」は、まさにこれでした。

毎回の配布で「ルールの貼り直しが要るかどうか」を1行目に書きます。
**コメントだけの変更なら要りません。**
