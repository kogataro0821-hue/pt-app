## 1. 何を実装したか

### 1-1. 契約者の一覧（設計書 §11.3 A-1）

管理者でログインすると、最初にこの画面が出ます。

- 契約者ごとに「表示名 / 契約者ID / 目標カロリー / 評価モード」を一覧表示
- **初期パスワードのまま**の契約者にバッジを出す（本人にパスワード変更を促すため）
- **無効**にした契約者にバッジを出す
- 作成が途中で止まった契約者は、上部に別枠で分けて表示

### 1-2. 契約者の作成（設計書 §11.3 A-2 / §6.5）

サーバーが無い構成なので、ブラウザだけで完結させています。

**管理者のセッションが切れない工夫**

素朴に `createUserWithEmailAndPassword` を呼ぶと、Firebase は「いま作ったユーザーで自動的にログイン」します。
つまり管理者が追い出されて、契約者としてログインした状態になってしまいます。

そこで、**一時的な別の Firebase インスタンス**を作り、そちらでユーザーを作成しています。
管理者のログイン状態には一切触れません。

**途中で失敗しても壊れない順番**

トランザクションが張れないため、順番で担保しています。

```
1. clients/{id} を「作成中」状態で先に作る   ← ここで重複IDを弾ける
2. 別インスタンスで Auth ユーザーを作る       ← 管理者のセッションは無傷
3. users/{uid} に権限を書く
4. clients/{id} を「完了」にする
```

どこで止まっても `clients/{id}` が「作成中」のまま残るので、
一覧の上部に「未完了の契約者」として出ます。開いて削除し、作り直せます。

### 1-3. 契約者の編集（設計書 §11.3 A-3）

| 項目 | 内容 |
|---|---|
| 基本情報 | 表示名・年齢・性別・身長・開始日・メモ |
| 目標 | カロリー・P・F・C・目標体重・目標体脂肪率・運動目標 |
| AI評価のトーン | やさしめ / 標準 / 辛口 / 非常に辛口（設計書 §26） |
| できること | 過去を何日前まで自分で修正できるか、食品登録の可否、レシピ登録の可否 |
| アカウント | 有効 / 無効の切り替え |

**契約者IDだけは変更できません。** データの置き場所（`clients/{ID}/...`）に使っているためです。
画面でもその旨を明示しています。

**PFCと目標カロリーのズレを警告します**

P×4 + F×9 + C×4 で計算した値が目標カロリーと10%以上ズレていると、注意書きを出します。
ただし**エラーにはしません**。意図的にずらす運用があり得るためです。

**無効化はデータを消しません（設計書 §6.6）**

`users/{uid}.active` を false にすることで、Rules 側で本人のデータすら読めなくなります。
記録は残るので、有効に戻せば元どおりです。

### 1-4. 入力の検証（テストあり）

契約者IDと目標値の検証は `packages/core` に置きました。**画面に依存しない純粋な関数**なので、テストできます。

**契約者ID**

```
□ ふつうのID（tanaka01, k.suzuki, sato-t）は通る
□ 大文字と前後の空白は自動で整える（  Tanaka01  → tanaka01）
□ 3文字未満 / 31文字以上は弾く
□ メールアドレスに使えない文字（空白, @, 日本語, +, /）は弾く
□ 記号で始まるIDは弾く
□ 予約語（admin, root, users, clients …）は弾く
```

契約者IDはログイン時にメール形式へ変換されるため、**メールの左側として成立する文字だけ**に絞っています。

**目標値**

```
□ 極端な値を弾く（カロリー 500〜6000 / たんぱく質 0〜500g など）
□ 体重・体脂肪率は未設定でも通る
□ 複数の問題をまとめて返す
□ PFCと目標カロリーのズレを警告（エラーにはしない）
```

## 3. 気をつけた点・既知の制約

### 3-1. Firebase Auth のユーザーは、ブラウザからは消せません

契約者の作成が「Auth ユーザーは作れたが、その後で失敗した」という状態で止まった場合、
使われていない Auth ユーザーが残ります。**これはブラウザからは削除できません**（Admin SDK が必要）。

同じ契約者IDで作り直そうとすると「すでに存在します」というエラーになります。
その場合の対処を、エラーメッセージに書いてあります。

> その契約者IDのログインアカウントはすでに存在します。
> 別のIDを使うか、Firebase コンソールで確認してください。

Firebase コンソール → Authentication → Users から手動で削除できます。
**めったに起きませんが、起きたときに何をすればいいか分かるようにしてあります。**

### 3-2. 初期パスワードの伝え方

初期パスワードは管理者が決めて、**口頭やメッセージで本人に伝える**運用です。
アプリからメールは送りません（契約者IDは実在しないメールに変換されるため）。

契約者が初回ログインすると、**パスワードを変更するまで先へ進めません**（Phase 3 で実装済み）。
変更が済んでいない契約者は、一覧に「初期パスワード」バッジが出ます。

### 3-3. 画面の切り替えについて

いまは画面の切り替えを内部の状態で持っています（URLは変わりません）。
画面が増える Phase 5 で、URLと連動する仕組みに置き換えます。
そのとき「ブラウザの戻るボタン」も正しく動くようになります。

## 5. あなたにお願いすること

**ファイルを差し替えて送るだけです。** Firebase の操作はありません。

送ったあと、アプリを開いて試してください。

1. 管理者でログイン → **契約者の一覧**が出る（まだ空のはず）
2. 「+ 追加」で契約者を1人作ってみる（ID・表示名・初期パスワード）
3. 作成後、編集画面で目標カロリーなどを設定して「保存する」
4. **いったんログアウト**して、その契約者IDと初期パスワードでログインしてみる
5. パスワード変更を求められる → 変更する
6. 「〇〇 としてログイン中」と出れば成功

これで **契約者の登録から本人のログインまでが一通り動く**ことが確認できます。
Phase 3 で手作業だった部分が、画面から行えるようになりました。

## 7. 実機確認で見つかった不具合と修正（追記）

### 症状
契約者が初回ログイン後にパスワードを変更しても、画面が変わらず、
同じ「パスワードの変更」画面に留まり続ける。
もう一度押すと「IDまたはパスワードが違います」と出る。

### 原因
**印を書く場所と、読む場所がずれていました。**

- 書く側: `clients/{clientId}.passwordChangedAt` に記録していた
- 読む側: `users/{uid}.passwordChangedAt` を見ていた

`users/{uid}` は契約者自身が書けません（自分を管理者に昇格させる経路を
作らないための、意図した制限です）。したがって書き先は `clients` 側で正しく、
**読み側を直すのが正解**でした。

パスワード変更そのものは1回目で成功していました。2回目に
「違います」と出たのは、すでに新しいパスワードに変わっていたためです。

### 修正
1. ログイン状態の読み込みを `loadProfile()` に切り出し、契約者の場合は
   `users/{uid}`（権限）と `clients/{clientId}`（初回変更の印）の2か所を読む。
2. パスワード変更の直後に読み直す `refresh()` を追加。
3. 万一 `clients` への記録だけが失敗しても画面から出られなくならないよう、
   セッション内のフラグを二重の安全網として持つ（UID付きなので、
   ログアウトして別の人がログインしても引きずらない）。

### 再発防止
権限テストに3件追加しました（合計57件）。

- 契約者は自分の `passwordChangedAt` を書ける
- 契約者は他人の `passwordChangedAt` を書けない
- 契約者は自分の `clients` ドキュメントを読める

1件目が、今回の不具合が二度と起きないことを保証します。
