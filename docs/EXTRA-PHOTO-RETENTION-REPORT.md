# 追加仕様 報告 — 写真の保存期間とトレーナーの確認

設計書には無かったもので、Phase 9〜10 の作業中に決めて入れました。
**番号は振っていません。** あとから振ると設計書の Phase 11・12 とぶつかるためです。

---

## 1. なぜ必要だったのか

無料枠は **1GB** しかありません。

写真は1枚あたりリサイズ後で数十〜数百KB。1〜10人が毎日3食撮ると、
**放っておけば必ず、いつか埋まります。** 埋まった日に何が起きるかというと、
写真が保存できなくなるのではなく、**記録全体が書き込めなくなります。**

写真は「数値を確かめるための材料」です。確かめ終われば役目は終わります。
永久に持つ理由がないものを持ち続けて、本体が止まるのが一番まずい。

---

## 2. 決めた形

| | |
|---|---|
| 保存期間 | **7週間（49日）** |
| 期限が来たら | 自動的に消える |
| トレーナーが確認したら | **その日の写真をすぐ消す** |
| 消える前 | 残り**2日**で契約者に警告 |

---

## 3. 「トレーナーの確認」は 1日確定とは別ものです

ここは分けるかどうかを相談して、**分ける**と決めました。

| | 1日確定 | トレーナーの確認 |
|---|---|---|
| 押す人 | 契約者 | 管理者 |
| 意味 | 「今日はもう食べません」 | 「食事・写真・運動を見ました」 |
| 解除 | 本人がいつでも | 管理者がいつでも |
| 写真 | 消えない | **その日のぶんが消える** |

**1つにまとめると、区別がつかなくなります。**
「契約者が書き終えたのか」と「トレーナーが見たのか」は、別の出来事です。
まとめてしまうと、契約者が確定した瞬間に写真が消えることになり、
トレーナーがまだ見ていない写真まで消えます。

### 取り消せます

押し間違いを直せないと、**「写真は消えたのに確認済みだけ残る」**という
一番困る状態から抜けられません。確認は取り消せるようにしてあります。
（消えた写真は戻りません。だから次の項目があります。）

---

## 4. 消える前に必ず伝えます

### 押す前の確認

「確認しました」を押すと、その前にこう出ます。

> この日の写真 **3枚** を削除します。
> 契約者の画面からも見えなくなります。**元には戻せません。**
> 食材・量・kcal・PFCの記録は消えません。

**黙って消すと、契約者から見れば写真が勝手に消えたことになります。**
枚数まで出しているのは、「何が消えるか」を数で分かるようにするためです。

### 契約者への事前警告（残り2日）

自動削除のほうも、黙っては消しません。
期限まで残り2日を切った写真がある日は、契約者の画面に出ます。

これはご要望どおりの形です。

> 「勝手に消えるでいいが、契約者の欄に残り2日になったものがある時に警告を出す」

残しておきたい写真があるなら、その2日のあいだに自分で保存できます。

## 5. 日数の計算（`@pt/core` の `photo/retention.ts`）

日付の計算は、画面ではなく `@pt/core` に置いています。
画面ごとに書くと、警告の画面と削除の判定で1日ずれます。

```ts
PHOTO_RETENTION_DAYS = 49        // 7週間
PHOTO_WARN_DAYS = 2

photoExpiresAt(createdAt)        // いつ消えるか
photoDaysLeft(createdAt, now)    // あと何日か（切り上げ）
isPhotoExpired(createdAt, now)
isPhotoExpiringSoon(createdAt, now)
photoWarnThreshold(now)          // Firestore へ問い合わせるための境目
photoExpiryThreshold(now)
photoExpiryLabel(createdAt, now) // 「あと2日で削除されます」
```

**残り日数は切り上げです。** 「あと0日」と出てまだ消えていない、という状態を作らないためです。
利用者から見て「あと1日」と書いてあるなら、まだ1日あるべきです。

`photoWarnThreshold` / `photoExpiryThreshold` は問い合わせ用です。
全部の写真を読んでから絞ると、無料枠の読み取り回数を無駄に使います。
境目の時刻を先に計算して、**その範囲だけ**を問い合わせます。

テストは17件です。

## 6. Rules

削除できる人を3通りに分けています。

```
match /clients/{cid}/days/{date}/photos/{photoId} {
  allow delete:
       isAdmin()                                      // ① 確認したトレーナー
    || (isClient(cid) && mayEdit(cid, date))          // ② 契約者（編集できる期間内）
    || (isClient(cid) && 作成から49日以上経過);         // ③ 期限切れの後片付け
}
```

③ があるのは、**Cloud Functions が無いから**です。
サーバ側で定期的に消す仕組みは、カード登録なしでは使えません。
なので「期限が切れた写真は、契約者自身のアプリが開いたときに消す」形にしました。

期限の判定には `request.time.toMillis()` を使います。
**端末の時計ではなく、サーバの時刻です。** 端末側の値を信じると、
時計を進めれば期間内の写真も消せてしまいます。

### `days/{date}` の書き込みも分けました

```
checkedAt / checkedBy   … 管理者だけが触れる
photoOldestAt           … 契約者も（編集期間の外でも）直せる
```

`photoOldestAt` は「その日で一番古い写真の時刻」です。
警告と自動削除の問い合わせを軽くするために持っています。
写真を消したあとに更新する必要があるので、**編集期間の外でも書ける**ようにしてあります。
ただし書けるのはこの1項目だけで、`hasOnly()` で縛っています。

Rules のテストに、期限切れ削除の可否を機械的に固定するテストを足しました。

## 7. 消えないもの

写真が消えても、**記録は消えません。**

| 消えるもの | 残るもの |
|---|---|
| 写真 | 食材の名前 |
| | 食べた量（g） |
| | kcal / P / F / C |
| | 運動・体重・メモ・コメント |

写真は数字を確かめるための材料であって、数字そのものではありません。
確かめた結果は数字として残ります。
