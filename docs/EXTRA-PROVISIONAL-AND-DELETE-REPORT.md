## 1. 仮の栄養値

### 何が問題だったか

マスタに無い食材を食べた日は、その分が**合計に1kcalも入りません**。

「カップヌードルとサラダチキン」の日が 0kcal で表示されます。記録したのに数字が動かないので、
**続ける気がなくなります。** 成分表示を撮っても同じでした。読み取った値は捨てていたからです。

### 何を変えたか

**マスタに無い食材にかぎり**、契約者が100gあたりの kcal/P/F/C を入れられるようにしました。

| 食材 | 契約者ができること |
|---|---|
| マスタに**ある**（白米 など） | 量(g)だけ。栄養値は**見るだけ** |
| マスタに**無い** | 量(g)と、**仮の栄養値** |

### ★ 一線をどこに引いたか

このアプリの原則は「栄養値を決めるのは管理者だけ」です。崩れると、
**「白米」が人によって156kcalだったり200kcalだったりして、数字を根拠にした指導ができなくなります。**

守り方を「禁止する」ではなく、**「入力欄を出さない」**にしました。

マスタにある食材には、そもそも打てる場所がありません。
**値がぶつかりうる場所に入力欄が無いので、ぶつかりようがありません。**

マスタに無い食材には、ぶつかる相手がいません。だから開けています。

### 画面の見え方

```
この日の合計   1,850kcal  P 142g  F 48g  C 190g
うち仮            95kcal  P  20g  F  1g  C   0g     ← 分けて出します
目標           2,000kcal  ...

  仮の値で記録した食材が1件あります。その分も上の合計に入っています。
  トレーナーが登録すると、正しい値に置き換わります。
```

食材の行にも「**仮**」の印を付け、数字と一緒に出します。
数字だけだと確定と見分けが付かず、印だけだと合計との関係が分かりません。

### 4つの入口それぞれ

| 入口 | どうなるか |
|---|---|
| **＋食材** | 名前がマスタに無ければ、その場で入力欄が出る |
| **成分表示から** | 読み取った値が**そのまま仮の値になる**（これまでは捨てていました） |
| **文章から** | いったん追加し、**その食材をタップして入れる**（下の理由） |
| **写真から** | 同上 |

**文章・写真の確認画面に4つの欄を並べませんでした。**
5品すべて未登録なら20個の欄が並び、スマホでは押し間違えます。
追加したあとにタップすれば、「＋食材」と同じ入力画面が開きます。

**1週間使ってみて窮屈だったら、確認画面に寄せます。** そのときは言ってください。

### 成分表示の読み取りは、直せるようにしました

読み取った数字を、そのまま入力欄に入れます。**AIのOCRは間違えるので、直せる形にしておきます。**

直した場合は、管理者に届く候補のメモに
「※ 読み取り値（263kcal・P10・F18.1・C65.3）を契約者が直しています」と自動で付きます。

**写真を見て「この数字で合っている」と判断したのに、実は本人が書き換えていた、という事故を防ぎます。**

### 管理者の画面

登録依頼に、値がどこから来たかを出すようにしました。

| 表示 | 意味 |
|---|---|
| **契約者が撮った成分表示** | 写真つき。表示と見比べられる |
| **契約者が手で入れた仮の値** | **裏付けはありません。**本人が分かる範囲で入れた数字 |

手入力のときは、こう添えます。

> この値はすでにその契約者の合計に「仮」として入っているので、
> **登録するとその日の数字が変わります。**

### 管理者が「仮」の食材を開いたとき

開いた時点で、欄には契約者の入れた値が入っています。
**そのまま保存しても、確定値には化けません。**

押しただけで確定すると、契約者の当て推量を確かめずに承認した形になります。
値を確定させる道は「登録依頼」の画面だけ、と決めました。

### AI評価に伝えること

```
※ 上の摂取量には、本人が仮に入力した値で計算されている食材が1件ぶん含まれています。
  まだトレーナーが確認していない数字なので、細かい数値の断定は避けてください。
```

伝えないと、確定した数字と同じ確からしさで「167gちょうど摂れています」と語ります。

## 2. 契約者の完全削除

### いままで

「無効にする」（ログインしても何も見られない・記録は残る）だけでした。
完全な削除は、**作成に失敗した契約者にしか**ありませんでした。

設計書 §6.6 には書いてあったのに、実装されていませんでした。

### ★ この画面の役目は「消すこと」ではありません

**間違って消させないこと**です。歯止めを4つ置きました。

| 歯止め | 中身 |
|---|---|
| 事前に量を見せる | 「記録のある日: 142日ぶん」「変更履歴: 3件」を数えてから確認画面を出す |
| **契約者IDを手で打たせる** | ぴったり一致するまでボタンが押せない |
| 消さない道を同じ画面に置く | 「無効にするで足りることがあります」と、削除の画面で示す |
| 進み具合を出す | 「毎日の記録 … 87/142」「これまでに 612 件消しました」 |

**2つ目が要です。**「本当によろしいですか？」は、3回目からは読まれません。
打たせるのは手間ですが、その手間が最後の歯止めになります。

### 消す順番

**下から消します。** 親を先に消すと、途中で失敗したときに
「どの契約者のものか分からない孤児」が大量に残ります。

```
毎日の記録（食事・運動・写真・メモ・評価 → 日データ）
  ↓
体のサイズ・お気に入り・レシピ・移行前のマスタ・変更履歴
  ↓
AIとのやりとり（本文 → セッション）
  ↓
登録依頼に残っている「この人の分」
  ↓
権限（users）→ 契約者そのもの（clients）
```

**途中で止まってもやり直せます。** 「いま在るものを数えて消す」だけなので、
もう一度実行すれば残りから続きます。

失敗したときは、こう出します。

> 途中で失敗しました。**消えたぶんは元に戻りません。**
> もう一度「完全に削除する」を実行すると、残りから続きます。

「失敗しました」だけだと、何も起きなかったと受け取られます。実際には途中まで消えています。

### ★ ログインアカウントだけは、消せません

他人の Firebase Auth アカウントを消すには管理者用の鍵（Admin SDK）が要ります。
**サーバーを持たない構成では、その鍵を置く場所がありません。**

削除が終わると、こう出ます。

> ログインアカウントだけは、ここでは消せません。
> Firebase の管理画面 →「Authentication」→ **taro@pt-app.local** を探して削除してください。
>
> 消すまで、このアドレスは使われたままになります。
> **同じ契約者ID（taro）で作り直すことはできません。**

### 変更履歴（audits）のルールを1つ緩めました

いままで、変更履歴は**誰にも消せませんでした**（管理者にも）。

そのままだと、消したはずの契約者の**食材名と日付が履歴に残り続けます。**
「完全に消した」とは言えません。

そこで **`update` は禁止のまま、`delete` だけ管理者に許しました。**

| | 前 | いま |
|---|---|---|
| 書き換える（改ざん） | できない | **できないまま** |
| 消す | できない | 管理者だけできる |

**書き換えを許すと、トレーナーが「別の数字だったことにする」ことができます。**
履歴が守っているのは、まさにそこです。消えていれば「無い」ことは分かるので、性質が違います。

テストも書き換えました（「管理者でも履歴を削除できない」→「管理者は履歴を削除できる」＋
「★ 管理者でも履歴は**書き換え**られない」を残す）。

### 事前エクスポートは作りませんでした

設計書には「二段階確認 + **事前エクスポート**」と書いてありました。
実際に使う場面（お試し用の契約者を消す）では書き出す先が無く、手間だけが増えると判断しました。

**設計書のほうを実態に合わせて書き直しました。** 必要になったら足せます
（消す前に全部読んでいるので、そこからJSONを作るだけです）。

## 3. 消し残しを防ぐ見張り

Phase 11B で作った見張り（`firebase/tests/coverage.test.ts`）に、**削除の見張りを足しました**。

**ルールに `match /◯◯` があるのに、`deleteClient.ts` で消していなければ、CIが止まります。**

```
ルールに match /moodLogs がありますが、deleteClient.ts で消していません。
契約者を完全に削除しても、ここのデータだけが残ります。
```

これが要るのは、Firestore が「親を消しても下位が残る」作りだからです。
新しいコレクションを足して、削除の処理に足し忘れると、
**消したはずの契約者のデータが、画面から見えないまま残り続けます。**
いちばんたちの悪い残り方で、しかも誰も気づけません。

あわせて次も見ています。

- 親より先に、下位のものを消しているか
- ログインアカウントが消えないことを、画面で伝えているか
- **変更履歴の書き換えが、誰にも許されていないか**

わざとルールを壊して、実際に止まることを確かめました（3つとも赤くなりました）。

### 固定した約束（主なもの）

| 確かめたこと |
|---|
| **★ マスタにある食材の栄養値は、入力欄そのものが出ない** |
| マスタに無い食材なら、仮の値を入れられる |
| 1つでも空欄なら、仮の値としては使わない（半端な値で合計を動かさない） |
| 仮の値は合計に入り、「うち仮」として取り出せる |
| **★ 管理者が登録すると、仮の値はマスタの値に置き換わり、印も消える** |
| **★ 管理者が「仮」の食材を開いて保存しても、確定値には化けない** |
| 手入力と成分表示を、管理者の画面で区別できる |
| **★ 契約者IDを打つまで、削除のボタンは押せない**（1文字違いでも押せない） |
| 消さずに済ませる道（無効にする）を、削除の画面に出す |
| **★ 途中で失敗したら、消えたぶんが戻らないことを隠さない** |
| 管理者は、契約者のデータを**16か所すべて**消せる |
| 契約者自身は、それらを勝手に消せない |

### 正直に

**Rules の287件は、まだ一度も実行されていません。** エミュレータのダウンロード先が
この作業環境から塞がれているためです。**最初に走るのは CI です。**

ルールの全文とテストを1行ずつ突き合わせ、期待値は検証しました（疑わしいもの0件）。
それでも赤くなる可能性はゼロではありません。赤くなったらすぐ直します。

### Rules の貼り直し

1. https://console.firebase.google.com → `pt-app` → **Firestore Database** → **ルール**
2. エディタの中を `Ctrl + A` → `Delete`（**継ぎ足さないでください**）
3. `C:\Users\user\Desktop\pt-app\firebase\firestore.rules` の中身を貼る
4. 「**公開**」を押す

**貼らないと、契約者の完全削除が途中で失敗します**（変更履歴が消せずに止まります）。
