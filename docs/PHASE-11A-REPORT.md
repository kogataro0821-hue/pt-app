## 3. 何を「守った」のか

テストは件数ではなく、**壊れてはいけない約束をいくつ固定したか**が大事です。
特に大事な4つを挙げます。

### ① 契約者は栄養値を決められない

```
契約者の画面に kcal / P / F / C の入力欄が出ないこと
未登録の食材は 栄養値0・登録待ち として渡されること
マスタにある食材は マスタの値がそのまま使われること
```

崩れると「白米」が人によって156kcalだったり200kcalだったりして、
**数字を根拠にした指導ができなくなります。**

### ② 契約者はトレーナーのコメントを書けない

書く欄も、編集・削除のボタンも出ないことを固定しました。
実装中、ここは一度**本当に書き換えられる状態**でした。
Rules 側でも塞いでありますが、画面側でも二重に押さえます。

### ③ 管理者は代わりにAI利用へ同意できない

送られるのは契約者が書いた食事の文章そのものです。
それを外部へ渡してよいかは、書いた本人以外が決められることではありません。
**管理者の画面にボタンが1つも無いこと**をテストにしました。

### ④ AI評価は、出す前に必ず検査される

```
病名が混ざった文章          → 表示しない・保存もしない
体に負担のかかるやり方       → 表示しない・保存もしない
疲れ・むくみ程度の体調の話    → 通す
免責は、評価があってもなくても必ず出す
```

指示文をどう書き換えても、**まずい文章が画面に出ない**ことを機械で保証します。

あわせて、AIに送る中身が数字だけであることも固定しました。
契約者IDも氏名も体重も、送っている項目の一覧に入っていないことを直接確かめています。

## 4. 書きながら分かったこと

### 4-1　入力チェックの文言が、画面に出ない作りになっていた

`ItemForm` には
「食材の名前を入力してください。」「量は0より大きく、5000g以内で…」
という文言がありますが、**そこへ到達できません。**
条件を満たすまで追加ボタンが押せないので、押した先の分岐に入らないためです。

**これは害のある不具合ではありません。**
押せない理由がその場で分かるほうが、押してから叱られるより親切です。
テストは実際の挙動（ボタンが押せないこと）を固定しました。
文言のほうは、いまは使われていない、ということだけ記録しておきます。

### 4-2　`vitest` の版が他とずれかけた

新しく入れると 4.x が入り、他のワークスペースの 3.2.7 と食い違いました。
**版が混ざると、片方でしか再現しない失敗が起きます。**
`package-lock.json` の入れ子の記録を外して、全ワークスペースで 3.2.7 に揃えました。
