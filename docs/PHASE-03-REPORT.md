## 1. 何を実装したか

### 1-1. Security Rules — このアプリの唯一の防衛線

`firebase/firestore.rules` に、設計書 §7 の内容をすべて実装しました。

Cloud Functions を持たない構成のため、**ここで拒否されないものは全部通ります。**
画面で隠すのは対策になりません。そのつもりで書いてあります。

| 守っていること | 実装 |
|---|---|
| 契約者間の完全分離 | データを `clients/{契約者ID}/` 配下に集約し、自分のIDと一致するときだけ通す |
| 権限の昇格禁止 | `users/{uid}` は管理者しか書けない。契約者が自分を管理者にする経路が存在しない |
| 目標値の保護 | 契約者が変えられるのは表示名・メモ・AI同意など5項目のみ。目標値と権限設定は触れない |
| 過去編集ウィンドウ | サーバー時刻（JST換算）から N日前まで。端末の時計をずらしても迂回できない |
| 1日確定の保護 | `finalized` の日は契約者が書き換えられない。管理者は可 |
| 写真のサイズ上限 | 400KB超を拒否。改造アプリから無料枠を食い潰されないため |
| 変更履歴の改ざん防止 | 追記のみ。管理者でも書き換え・削除ができない |
| 無効化された契約者 | `active: false` なら自分のデータすら読めない |
| 未登録アカウント | Firebase Auth に勝手に登録しても、`users` が無いので何も見えない |

**実装上の工夫**: Firestore は1リクエストあたり `get()` / `exists()` を10回までしか呼べません。
判定関数の呼び出し回数を数え、条件の並び順（安い判定を先に置く）も調整してあります。

### 1-2. 権限テスト — 55件

`firebase/tests/rules.test.ts` に、Rules の全分岐を検証するテストを書きました。

特に重要なもの:

```
□ 契約者A → 契約者B のプロフィール・食事・食品・体重・AI会話  → すべて拒否
□ 逆向き（B → A）も同様に拒否
□ 契約者が自分を管理者に昇格 → 拒否
□ 契約者が自分の clientId を書き換えて他人になりすます → 拒否
□ 契約者が自分の目標カロリーを変更 → 拒否
□ 契約者が編集ウィンドウの日数を伸ばす → 拒否
□ 10日前の食事を契約者が書き込む（ウィンドウ外） → 拒否
□ ただし読むことはできる（設計書 §2「過去の日付を閲覧可能」）
□ 確定済みの日を契約者が書き換える → 拒否
□ 400KB超の写真 → 拒否
□ 変更履歴の書き換え・削除 → 管理者でも拒否
□ 無効化された契約者 → 自分のデータも拒否
□ 未認証 → 全拒否
□ 管理者 → 全契約者に読み書き可
```

### 1-3. ログイン画面

| 画面 | 内容 |
|---|---|
| ログイン | 「契約者」「管理者」の切り替え。契約者はID、管理者はメール |
| パスワード変更 | 現在のパスワードで本人確認してから変更。8文字以上 |
| 初回強制変更 | 契約者が一度もパスワードを変えていなければ、変更するまで先へ進めない |
| 登録されていない | ログインはできたが権限が無い場合の案内 |
| 無効化された | アカウントが無効な場合の案内 |
| ホーム | 誰としてログイン中かを表示（Phase 5 でカレンダーに置き換え） |

**契約者IDの扱い（設計書 §6.2）**

```
tanaka01  →  tanaka01@pt-app.local
```

端末側で機械的に変換します。サーバーに「そのIDは存在しますか？」と問い合わせないため、
**契約者IDの一覧を外部から調べることができません。**

ログイン失敗時は、IDが違ってもパスワードが違っても
「IDまたはパスワードが違います」の一択にしてあります。区別すると存在を教えてしまうためです。

### Rules テストを私の環境で実行できなかった理由

Rules のテストには Firestore Emulator が必要で、その本体（Javaのプログラム）を
Google のサーバーからダウンロードする必要があります。
**私の作業環境はネットワークが制限されており、そのダウンロードが拒否されました。**

そこで、**GitHub Actions で必ず実行されるようにしました。**

```
main に push
   ↓
型チェック・lint・テスト・ビルド
   ↓
★ Security Rules テスト（55件）
   ↓
すべて緑なら公開。ひとつでも赤なら公開しない
```

つまり **Rules テストが通らない限り、アプリは更新されません。** 公開中のアプリは前の版のまま残ります。

初回の push で、実際に55件が通るかが分かります。もし落ちた場合は、
Actions の画面に「どのテストが、なぜ落ちたか」が日本語で出るので、それを見て直します。

## 4. あなたにお願いすること

Phase 3 を動かすには、あと3つ必要です。**すべてブラウザの操作です。**

### ① 新しいファイルを送る

いつもどおり、ZIP を展開して上書き → GitHub Desktop で Commit → Push。

### ② Security Rules を Firebase に反映する

**ここが一番大事です。** リポジトリに書いた Rules は、Firebase に登録しないと効きません。

1. GitHub で `firebase/firestore.rules` を開く
2. 中身を全部コピー
3. Firebase コンソール → Firestore → 「**ルール**」タブ
4. 中身を全部消して貼り付け
5. 「**公開**」

> Rules を変更するたびにこの作業が必要です。毎回やるのが面倒なら、
> 自動化もできます（GitHub に鍵を1つ登録する作業が一度だけ必要）。ご希望なら用意します。

### ③ 管理者アカウントを1つ作る

権限の台帳（`users`）は管理者しか書けない仕組みなので、**最初の1人だけは手作業**です（設計書 §6.4）。

**3-1. Authentication でユーザーを作る**

Firebase コンソール → Authentication → 「Users」タブ → 「**ユーザーを追加**」

| 項目 | 入力 |
|---|---|
| メールアドレス | 管理者が使うメールアドレス |
| パスワード | 8文字以上の好きなパスワード |

作成後、一覧に表示される「**ユーザーUID**」（`AbC123...` のような長い文字列）をコピーします。

**3-2. Firestore に権限の台帳を作る**

Firebase コンソール → Firestore → 「**コレクションを開始**」

| 項目 | 入力 |
|---|---|
| コレクションID | `users` |
| ドキュメントID | **さっきコピーしたUID** |

フィールドを3つ追加します。**型を間違えると動きません。**

| フィールド名 | 型 | 値 |
|---|---|---|
| `role` | string | `admin` |
| `clientId` | null | （値なし） |
| `active` | boolean | `true` |

**3-3. ログインしてみる**

アプリを開いて「管理者」タブ → 3-1 のメールとパスワードでログイン。

「**管理者としてログイン中**」と出れば成功です。

## 5. 気をつけていること

### リポジトリが Public であることについて

Rules の中身は誰でも読めます。これは問題ありません。
Rules は「見られたら破られる」種類のものではなく、サーバー側で強制されるためです。

ただし、**穴があれば見つけられやすくなる**のは事実です。だから
権限テスト55件を CI の必須項目にして、緑でない限り公開できないようにしました。

### Firebase Auth に誰でも登録できてしまう件

apiKey が公開されているため、第三者が勝手にアカウントを作ることは技術的に可能です。
ただし `users` ドキュメントは管理者しか作れないので、
**登録しても「ログインできるが何も見えない」状態**にしかなりません。
共通の食品マスタも読めないようにしてあります。

### 画面側の権限判定について

ログイン後の画面は role によって出し分けていますが、
**これは見せ方の問題でしかありません。** 画面のコードを書き換えても、
Rules が拒否するので他人のデータは1バイトも取れません。
