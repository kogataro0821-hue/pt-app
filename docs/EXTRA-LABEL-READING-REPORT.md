# 追加仕様 報告 — 成分表示の読み取り

設計書には無かったもので、Phase 9〜10 の作業中に決めて入れました。
**番号は振っていません。** あとから振ると設計書の Phase 11・12 とぶつかるためです。

---

## 1. 何ができるようになったのか

既製品のパッケージにある **栄養成分表示を撮ると**、

1. AIが読み取り
2. **100gあたりに換算**して
3. **登録依頼の候補**として、写真ごと管理者へ送る

管理者が承認すると、**契約者が食べたグラム数に換算されて、過去の記録にも入ります。**

---

## 2. 4つ目の入口にしました

```
＋食材        文章から        写真から        成分表示から   ← new
```

はじめは「＋食材」で名前を打ったあとに撮る形にしていました。**順番が逆でした。**

既製品を食べたとき、利用者が最初に手にしているのは**パッケージ**です。
そして撮れば、商品名も1食分のグラム数も表示に書いてあります。
**打つ前に読める情報を、打たせる理由がありません。**

読み取ったあとの画面では、

- **名前** … パッケージから読み取った商品名が入る（直せる）
- **食べた量** … 「1食分 57g」と書いてあればそれが入る（半分なら直せる）

「100g当たり」表示の商品では、**量の欄は空のまま**にしています。
100gを勝手に入れると、**直し忘れがそのまま記録に残ります。**

---

## 3. 読み取った数値は、その場では記録に入りません

ここが一番大事なところです。

```
契約者が撮る
  ↓
100gあたりに換算（決定論的な計算）
  ↓
「登録待ち」として記録に残る … 合計には入らない
  ↓
登録依頼として管理者へ（写真つき）
  ↓
管理者が承認
  ↓
食べたグラム数に換算されて、記録に反映される  ← ここで初めて合計に入る
```

袋に書いてある数字なら信用してよさそうに見えます。ですが、

- 桁の読み違い（`263` を `26.3` と読む）
- **参考値の取り違え**（カップ麺には「1食263kcal」と「めん・かやく243kcal」が並んでいる）

が起こります。取り違えると **2割ずれます。**

Phase 9 で決めた線は動かしません。

> **全員のマスタに入る数値を決めるのは管理者。**

---

## 4. 写真も一緒に送ります

これは、ご指摘で方針が変わったところです。

> 「ん？まって、なんで管理者側でもう一回取り直さないといけないの？物理的に無理じゃない？」

そのとおりでした。**管理者は契約者と別の場所にいます。** 撮り直せません。
最初は数字だけを送る設計にしていましたが、それでは管理者は確かめようがありません。

**数字だけでは、受け取った側が確かめられません。**
「1食263kcal」と「参考値めん243kcal」のどちらを読んだかを見抜けるのは、
表示そのものを見たときだけです。

なので、読み取った成分表示の写真を依頼に添えます。

### ただし溜め込みません

依頼を片付けると、**この写真も一緒に消えます。** 確かめ終われば役目は終わります。

マスタ側に永久保存する案もありましたが、こちらのご判断で見送りました。

> 「いや、保存したら消えるでもいいのでは？」

無料枠1GBの中で、確認済みの写真を持ち続ける理由がありません。

---

## 5. 換算は AI にやらせていません（`@pt/core` の `food/label.ts`）

AIがやるのは **文字を読むところまで**です。
そこから100gあたりを出す計算は、テスト済みのコードでやります。

```ts
labelToPer100g(reading)   // 読み取り → 100gあたり
labelBasisLabel(reading)  // 「1食57gあたりの表示から換算」
```

| 表示の形 | やること |
|---|---|
| **100gあたり** | そのまま |
| **100mlあたり** | 100gとして扱う（**注記を必ず付ける**） |
| **1食◯gあたり** | `値 ÷ ◯ × 100` |
| **1食あたり（g数なし）** | **換算しない**（`need-serving-grams` を返す） |

### 推測しません

1食あたりの表示でグラム数が書いていないとき、**100gと決めつけません。**
分からないものは分からないと返します。

推測して入った値は、そのあと誰にも見分けがつきません。

### 足りない項目の埋め方

| 状況 | やること |
|---|---|
| 炭水化物が無く、糖質と食物繊維がある | **炭水化物 = 糖質 + 食物繊維** |
| 食塩相当量が無く、ナトリウム(mg)がある | **食塩 = ナトリウム × 2.54 ÷ 1000** |

どちらも決まった換算です。推測ではありません。

### 実物で検算しました

カップ麺の実際の表示（1食57g・263kcal）で、

```
263 ÷ 57 × 100 = 461.4 kcal/100g   ✅
```

テストは17件です。

## 6. 依頼の作り方（Phase 9 の続き）

候補は、依頼の**下位**に置いています。

```
foodRequests/{照合キー}                    ← 契約者は書けるが読めない
  └ from/{契約者ID}                        ← 自分の1件だけ
       { variant, count, dates,
         candidatePer100g,                 ← 読み取った100gあたり
         candidateNote,                    ← 「1食57gあたりの表示から換算」
         candidatePhoto }                  ← 成分表示の写真
```

**候補が他の契約者から読めては意味がありません。**
何を食べたかが分かってしまいます。Phase 9 の「書けるが読めない」をそのまま使っています。

### 候補は上書きします

同じ食材を撮り直したら、あとから撮ったほうを残します。新しいほうが正しいためです。
撮っていない回では触りません（前の候補が残ります）。

### 写真のサイズ制限

Rules 側で **400,000バイト未満**に縛っています。
Firestore の1ドキュメント上限は1MBです。制限が無いと、
大きな写真1枚でドキュメントが書き込めなくなり、依頼そのものが積めなくなります。

## 7. 承認したときの動き

管理者の「登録依頼」画面で、候補の値と写真を見ながら判断します。

| ボタン | やること |
|---|---|
| **新しく登録する** | 候補の値を初期値としてマスタを作る |
| **既存の食材にまとめる** | 表記ゆれとして既存へ吸収する |

どちらでも、保存すると **過去の記録の「登録待ち」が自動で置き換わります。**

これもご要望どおりの形です。

> 「いや、kcal PFCも入力…認証が出来次第そのグラムに変換して、記録に残る」

置き換えるのは、依頼に記録してある**日付だけ**です。
全員の全日分を調べ直すと、無料枠の読み取り回数を使い切ります。
置き換えた記録には、誰がいつ置き換えたかを契約者ごとに残しています。

**保存すると、依頼も一緒に片付きます。** 別に「完了」を押す必要はありません。

## 8. 実装中に直したこと

### 編集中に写真が消えていた

（ご報告いただいたものです）

依頼の写真を、画面の「何もしていない状態」のときだけ描画していました。
「新しく登録する」を押した瞬間に、**判断材料である写真が画面から消えていました。**
値を入れるときこそ見たいものです。依頼を開いているあいだは常に出るようにしました。

### 保存しても依頼が消えなかった

同じくご報告いただいたものです。過去の記録を置き換えたあと、
依頼を片付ける処理を呼んでいませんでした。**保存で全部終わる**ようにしました。
