# Phase 9 報告 — 数値の統一と登録依頼

## 1. 何を解決したのか

これまで、食品の栄養値は契約者ごとの個人マスタに入っていました。
つまり **契約者が自分で 100g あたりの kcal / P / F / C を決められた** ということです。

その状態を続けると、こうなります。

| 契約者 | 「白米」の100gあたり |
|---|---|
| 田中さん | 156kcal |
| 鈴木さん | 168kcal |
| 佐藤さん | 200kcal（AIの推定をそのまま保存） |

同じ食材の数字が人によって違うと、トレーナーが数字を根拠に指導できません。
「今週はP不足です」と言っても、その P が何を基準にした値なのか説明できないからです。

Phase 9 でこれを直しました。決め方を、**知っている側が担当する形**に変えています。

| 決めること | 誰が | 理由 |
|---|---|---|
| 食べた量（g） | 契約者 | 本人しか知らない |
| 100gあたりの栄養値 | 管理者 | 調べる人が決めるもの |

---

## 2. 契約者の画面から栄養値の入力欄が消えました

食材を追加するとき、契約者が入れるのは **名前と量だけ** になりました。

- マスタにある食材 … 100gあたりの値が「表示だけ」で出ます（編集不可）
- マスタに無い食材 … 量だけ記録し、管理者へ登録依頼が飛びます

記録は止めません。止めると続かなくなるからです。
未登録の食材は「栄養値は登録待ち」と表示され、その日の合計には含めません。
画面下部に「栄養値が未確定の食材が◯件あります」と出ます。

**合計が黙って狂うより、含まれていないと明示するほうが安全です。**
0kcal として足してしまうと、実際より少なく見える合計を根拠に指導することになります。

## 3. 管理者に2つの画面ができました

### 食品マスタ（`/foods`）

一覧・追加・編集・削除。検索は照合キーで行うので、「とりムネ」と打っても「鶏むね肉」に当たります。

保存前に2つの警告が出ます。

1. **似た食材がすでにあります** — 同じ食材を2件作る前に気づけます
2. **PFCから計算すると約◯kcalですが、◯kcalと入力されています** — 桁の打ち間違い

2 は止めません。野菜は食物繊維のぶん計算値が高く出るのが正常だからです
（ブロッコリー: 実際37kcal／計算値53kcal）。2倍以上ずれたときだけ知らせます。

### 登録依頼（`/foods/requests`）

契約者が記録した未登録の食材が積まれます。やることは2つのどちらかです。

| | いつ | 何が起きるか |
|---|---|---|
| **新しく登録する** | 本当に新しい食材 | マスタに追加。使われた表記は別名として自動で入る |
| **◯◯にまとめる** | 書き方が違うだけ | 既存の食材に別名として吸収。以後その書き方でも当たる |

どちらのあとにも、こう聞きます。

> この食材を使っている記録が **3件** あります（2日分）。新しい値を入れますか？
> 押さなければ過去はそのままです。押した場合は変更履歴に残ります。

**押さなければ、過去の数字は1つも変わりません。**
過去の記録が黙って書き換わると、契約者が自分の記録を信用できなくなります。

置き換えるのは「未確定」の食材だけです。
すでに数値が入っている食材は、名前が同じでも触りません。
誰かが確認して入った数字を、あとから黙って変える根拠がないためです。

## 4. 名前のぶれ対策（ご要望の「予測変換もうまく調整してほしい」）

手打ちが増えると、同じ食材の依頼が何件も立ちます。
これを放置すると、統一のために作った仕組みが逆に分裂を生みます。

5層で防いでいます。

| | 仕組み | 例 |
|---|---|---|
| 1 | **照合キー** — 全角半角・空白・カタカナ/ひらがな・大文字小文字・中黒を吸収 | `ｻﾗﾀﾞ ﾁｷﾝ` → `さらだちきん` |
| 2 | **別名** — 管理者が「鶏胸肉、とりむね、ムネ肉」を登録できる | どれで打っても当たる |
| 3 | **似た名前の警告** — 依頼を出す前に既存へ寄せる | 「似た食材があります」 |
| 4 | **AIの出力も同じ照合を通す** | 写真・文章から起こした食材も同じ経路 |
| 5 | **依頼側でもまとめる** — 照合キーがドキュメントIDなので同じ食材の依頼は自動で1件になる | 3人が別表記で使っても依頼は1件 |

意図的に**吸収しない**ものもあります。

- 長音（ー）… 「ラーメン」と「ラメン」は別物
- 小書き文字（ッャュョ）… 「ホッケ」と「ホケ」は別物

ここまで吸収すると、別の食材まで巻き込みます。

なお、`鶏むね肉` と `とりむね肉` は照合キーでは一致しません（漢字と読みは別物のため）。
これは 3 の「似た食材があります」と 2 の別名で拾う設計です。

## 5. 安全面でいちばん考えたところ

登録依頼には「誰が使ったか」が入ります。ここに落とし穴がありました。

依頼を1つのドキュメントにまとめて `clientIds: ['alice', 'bob']` と持たせると、
配列に自分を足すために **契約者がそのドキュメントを読める必要が出ます**。
読めるということは、**他の契約者が何を食べたかを推測できる**ということです。

> 契約者Aが契約者Bの情報を見ることは絶対にできない

この前提が崩れます。そこで形を変えました。

```
foodRequests/{照合キー}              ← 契約者は「書けるが読めない」
  └ from/{契約者ID}                 ← 自分の1件だけ書ける・他人のぶんは読めない
       { variant, count, dates }
```

- 増分は `increment` / `arrayUnion` を使うので、**書く前に読む必要がありません**
- 集計するのは管理者だけです
- 他人になりすまして書くこともできません（`isClient(clientId)` で判定）

Rules に13件のテストを追加し、この「書けるが読めない」を機械的に固定しました。

あわせて、`clients/{cid}/foods`（個人マスタ）への契約者の書き込みを塞ぎました。
移行前のデータを管理者が整理できるよう、読み取りだけ残してあります。

## 6. 実装中に見つけて直したこと

**照合キーと依頼IDが食い違う可能性がありました。**

依頼IDを作るとき、Firestore が受け付けない文字（`/` `#` `$` `[` `]`）を
使う側でそれぞれ落としていました。すると「1/2カット」のような名前で、

- 照合キー … `1/2かっと`
- 依頼のID … `1_2かっと`

と食い違い、あとから過去の記録を置き換えるときに **黙って取りこぼします**。
エラーも出ないので、気づくのは「置き換えたのに数字が変わらない」と言われたときです。

キーの作り方を `foodKey` の1か所に統一し、長さも100文字に揃えました。
この性質を固定するテストを6件追加しています。
